# ADR-008: WebRTC Egress 녹화 전략

## 상태

**Accepted** (2025-05)

## 맥락

화재 감지 이벤트 발생 시 실시간 CCTV 영상을 녹화하여 보관해야 한다. 녹화된 영상은 이후 화재 이벤트 이력에서 재생 가능해야 한다.

### 요구사항

1. **자동 녹화**: 화재 감지 즉시 녹화 시작, 스트리밍 종료 시 녹화 중단
2. **저장소**: 영구 보관이 가능한 오브젝트 스토리지
3. **접근 제어**: 해당 방(Room) 멤버만 녹화 영상 재생 가능
4. **엣지 부담 최소**: 엣지 디바이스에 추가 부하 없이 녹화

### 후보 녹화 방식

| 방식                            | 녹화 위치    | 엣지 부담      | 품질 제어       | 구현 복잡도 |
| ------------------------------- | ------------ | -------------- | --------------- | ----------- |
| **서버사이드 Egress (LiveKit)** | SFU 서버     | 없음           | SFU 제어        | 낮음 (내장) |
| **클라이언트사이드 녹화**       | 모바일 앱    | 없음 (앱 부담) | 클라이언트 의존 | 중간        |
| **엣지 디바이스 로컬 녹화**     | Raspberry Pi | 높음           | 엣지 제어       | 낮음        |
| **별도 미디어 서버 녹화**       | 전용 서버    | 없음           | 서버 제어       | 높음        |

## 결정

**LiveKit Egress를 사용한 서버사이드 녹화 + S3 저장**을 선택한다.

### 녹화 흐름

```
1. 화재 감지 → POST /embedded/fire-event/publish
2. 서버: FireEvent 생성 + LiveKit Room 생성
3. 서버: Egress API로 Room Composite Egress 시작
   → LiveKit Egress 서비스가 Room의 모든 트랙을 녹화
   → 녹화 파일을 S3에 직접 업로드
4. 엣지 디바이스: LiveKit Room에 참여하여 영상 발행
5. 스트리밍 종료: 엣지 디바이스가 Room에서 퇴장
6. LiveKit Webhook(egress_ended) → 서버에 S3 경로 전달
7. 서버: MediaRecord에 S3 경로 저장
8. 모바일 앱: GET /fire-event/{id}/record → S3 Presigned URL 수령 → 영상 재생
```

### Egress 설정

| 항목               | 값                | 근거                                   |
| ------------------ | ----------------- | -------------------------------------- |
| Egress 유형        | Room Composite    | Room 내 모든 트랙을 하나의 파일로 합성 |
| 출력 포맷          | MP4 (H.264 + AAC) | 모바일 앱에서 범용 재생 가능           |
| 저장소             | AWS S3            | 영구 보관, Presigned URL로 접근 제어   |
| Presigned URL 만료 | 1시간             | 공유 링크 유출 시 피해 시간 제한       |

## 대안 분석

### 클라이언트사이드 녹화 (모바일 앱에서 MediaRecorder) — 기각

- 장점: 서버 추가 비용 없음
- 단점:
  - 시청자가 없으면 녹화 불가 (앱이 열려 있어야 함)
  - 앱이 백그라운드로 전환되면 녹화 중단
  - 녹화 품질이 클라이언트 기기 성능에 의존
  - 녹화 파일을 다시 서버에 업로드해야 함 → 이중 전송

### 엣지 디바이스 로컬 녹화 (OpenCV VideoWriter) — 기각

- 장점: 네트워크 독립, 가장 원본에 가까운 품질
- 단점:
  - Raspberry Pi의 SD 카드 용량 제한 (32GB)
  - YOLO 추론 + 스트리밍 + 녹화 동시 수행 시 CPU 과부하
  - 녹화 파일을 서버로 업로드하는 별도 파이프라인 필요
  - SD 카드 수명 단축 (쓰기 집약적)

### 별도 미디어 서버 녹화 (FFmpeg + RTMP) — 기각

- 장점: 녹화 품질/포맷 완전 제어
- 단점:
  - WebRTC → RTMP 프로토콜 변환 필요
  - 별도 미디어 서버 운영 비용
  - LiveKit과 별개 시스템이므로 통합 복잡도 증가
  - LiveKit Egress가 이미 동일 기능을 내장

## 결과

### 긍정적

- 엣지 디바이스에 녹화 부담 없음 → YOLO + 스트리밍에 집중
- LiveKit Egress가 Room 생성과 동시에 녹화 시작 → 별도 제어 불필요
- S3에 직접 저장하므로 서버 디스크 부담 없음
- Presigned URL로 녹화 영상 접근 제어 + CDN 없이 직접 전달

### 부정적

- LiveKit Egress 서비스가 Docker 컨테이너로 별도 실행되어야 함 → 리소스 추가 사용
- Room Composite Egress는 Chrome Headless를 내부적으로 사용 → 메모리 소모 높음
- Egress 실패 시 녹화 누락 가능 → 현재 재시도 로직 미구현
- 로컬 개발 환경에서는 MinIO를 S3 대안으로 사용해야 함

### 트레이드오프 요약

```
엣지 부담 제로 + 자동 녹화 + S3 영구 보관  ←→  Egress 서비스 리소스 + 실패 시 녹화 누락
```
